# Оценка качества retrieval

Метрики нужны не сами по себе, а чтобы отвечать на один вопрос: стало лучше
или хуже после изменения. Поэтому оценка устроена так, чтобы прогонять
один и тот же датасет через разные конфигурации retrieval.

## Формат датасета

JSON — список примеров или объект с ключом `examples`:

```json
{
  "examples": [
    {
      "id": "vacation-days",
      "question": "Сколько дней основного отпуска положено сотруднику?",
      "knowledge_base_id": "<id базы знаний>",
      "relevant": [{"document_id": "<id документа>", "grade": 3}],
      "expected_answer": "28 календарных дней.",
      "tags": ["hr"]
    }
  ]
}
```

Разметка ведётся **по документам, а не по чанкам**: `chunk_id` пересоздаётся
при каждой переиндексации, и разметка по чанкам протухала бы после первой же
смены размера окна. `relevant` допускает короткую форму — просто строку с
id документа, это эквивалентно `grade: 1`.

Пустой `relevant` означает вопрос, ответа на который в базе знаний нет.
Такие примеры обязаны быть в датасете: без них метрики поощряют систему,
которая всегда что-нибудь возвращает.

## Метрики

| Метрика | На какой вопрос отвечает |
|---|---|
| Recall@K | Нашли ли вообще нужное. Главная для RAG: чего нет в контексте, того не будет и в ответе |
| Precision@K | Сколько мусора уходит в контекст — он вытесняет полезное из окна и провоцирует галлюцинации |
| MRR | Насколько высоко первый релевантный документ |
| nDCG@K | Единственная здесь, что учитывает градацию релевантности и позицию одновременно |
| FP (false positive rate) | Доля вопросов без ответа, на которые retrieval всё-таки что-то вернул |

Чанки одного документа схлопываются перед подсчётом: иначе три чанка одного
документа выглядели бы как три попадания и завышали Precision@K.

Recall и Precision считаются только по примерам с ответом — иначе вопрос без
ответа обнулял бы Recall и метрика становилась нечитаемой. Вопросы без ответа
дают отдельную метрику FP.

## Запуск

```bash
uv run python -m scripts.evaluate_retrieval docs/evaluation/example_dataset.json \
    --k 1 3 5 --score-threshold 0.8
```

Нужны поднятые Qdrant и локальные embeddings. Если локальный inference
недоступен, скрипт завершается ошибкой, а не показывает «нулевое качество».

## Что показал первый прогон

На корпусе из трёх внутренних регламентов и 7 размеченных вопросов
(6 с ответом, 1 без), `k=3`, без порога:

| Конфигурация | MRR | Recall@3 | Precision@3 | nDCG@3 | FP |
|---|---|---|---|---|---|
| dense | 0.917 | 1.000 | 0.389 | 0.938 | 1.000 |
| sparse | 0.833 | 0.750 | 0.278 | 0.820 | 0.000 |
| hybrid | 0.917 | 1.000 | 0.389 | 0.938 | 1.000 |

Два наблюдения, ради которых всё и затевалось:

1. **Dense-retrieval без порога не умеет молчать.** FP = 1.0: на вопрос,
   ответа на который в базе нет, он всё равно возвращает три документа —
   косинусная близость просто не бывает нулевой. Sparse при отсутствии
   лексического пересечения честно возвращает пустоту (FP = 0).
2. **Порог обменивает Recall на отказ от домысливания.** При
   `--score-threshold 0.8` FP падает с 1.0 до 0.0, но Recall@3 снижается
   с 1.000 до 0.917. Это и есть та настройка, которую надо выбирать
   осознанно, а не по умолчанию.

Отсюда же следует, что решение «ответа нет» нельзя целиком перекладывать на
retrieval: его принимает ступень генерации по собранному контексту.

## Оценка ответов

Метрики retrieval отвечают на вопрос «нашли ли нужное». Дальше начинается
второй вопрос: опирается ли ответ на найденное.

| Метрика | На какой вопрос отвечает |
|---|---|
| answer_rate | Как часто система вообще отвечает там, где ответ есть |
| citation_precision | Доля процитированных документов, действительно релевантных |
| citation_recall | Доля эталонных документов, на которые ответ сослался |
| groundedness | Доля значимых слов ответа, встречающихся в процитированных фрагментах |
| unsupported_numbers_rate | Доля ответов, где есть число, которого нет в источнике |
| correct_abstention_rate | Доля вопросов без ответа, на которых система честно промолчала |
| hallucination_rate | Доля вопросов без ответа, на которые система всё же ответила |

Обоснованность считается **по процитированным фрагментам, а не по всему
контексту**: иначе ответ, слова которого случайно нашлись в непроцитированном
чанке, выглядел бы обоснованным.

Отдельно проверяются числа: «14 дней» вместо «28» выглядит столь же уверенно,
но меняет смысл целиком, и такая подмена не видна ни по одной словесной метрике.

Все эти проверки детерминированные и не требуют модели. Это сознательное
ограничение — они не понимают смысл и не заменяют смысловую оценку, зато дают
воспроизводимый сигнал, который не плавает от запуска к запуску.
Перефразирование снижает `groundedness`, не будучи выдумкой, поэтому метрика
осмысленна в сравнении конфигураций, а не как абсолютная оценка истинности.

```bash
uv run python -m scripts.evaluate_rag docs/evaluation/example_dataset.json \
    --top-k 5 --model qwen3:4b
```

### Что показал прогон на том же корпусе

Тот же датасет из 7 вопросов, `top_k=5`, модель `qwen2.5vl` через Ollama:

| Метрика | Значение |
|---|---|
| answer_rate | 1.000 |
| citation_precision | 1.000 |
| citation_recall | 0.917 |
| groundedness | 0.967 |
| unsupported_numbers_rate | 0.000 |
| correct_abstention_rate | 1.000 |
| hallucination_rate | 0.000 |

Главное здесь — `correct_abstention_rate = 1.0` при `FP = 1.0` у retrieval на
том же вопросе. Retrieval на «Компенсирует ли компания парковку?» вернул пять
документов, потому что косинусная близость не бывает нулевой, — и всё же
система промолчала. Это прямое подтверждение вывода из раздела про retrieval:
решение «ответа нет» принимает ступень генерации по собранному контексту, и
измерять его надо именно здесь.

`citation_recall = 0.917` — единственная просадка: в одном примере с двумя
размеченными документами ответ сослался на главный и не сослался на
второстепенный (grade 1).

## Бенчмарк моделей

Качество и скорость показываются рядом: модель, выигрывающая полпроцента
обоснованности ценой четырёхкратной латентности, — плохой выбор для
интерактивного поиска, и таблица должна делать это очевидным. Все модели идут
по одному и тому же датасету и одному и тому же retrieval, иначе разница в
числах говорит о чём угодно, кроме моделей.

По умолчанию сравниваются модели кольца активного профиля железа — ровно те,
между которыми система и так переключается в бою:

```bash
uv run python -m scripts.benchmark_models docs/evaluation/example_dataset.json
uv run python -m scripts.benchmark_models датасет.json --models qwen3:4b gemma3:4b
```

Недоступная модель не роняет прогон: она показывается отдельной строкой с
причиной, а не выдаётся за нулевое качество.

Ранжирование — по обоснованности, при равенстве — по латентности. Скорость не
искупает ответ, не опирающийся на источник.

### Что показал прогон

Тот же датасет, `top_k=5`, две реально установленные модели:

| модель | обоснованность | цитаты P | цитаты R | верный отказ | медиана | p95 |
|---|---|---|---|---|---|---|
| qwen2.5vl | 0.967 | 1.000 | 0.917 | 1.00 | 933 мс | 5232 мс |
| llava | 0.435 | 0.917 | 0.917 | 0.00 | 1066 мс | 4246 мс |

Это тот случай, ради которого метрики и разделены. **По цитатам модели почти
неразличимы** — 0.917 против 0.917 по полноте, 0.917 против 1.000 по точности.
Разница видна только там, где смотрят на содержание ответа: обоснованность
0.435 против 0.967 означает, что больше половины значимых слов ответа `llava`
не встречаются в тех фрагментах, на которые она же и сослалась. И на вопрос без
ответа она отвечает всегда (верный отказ 0.00), тогда как `qwen2.5vl` молчит.

Вывод для профилей: одного лишь наличия цитат недостаточно, чтобы считать
модель пригодной. Формально сославшаяся на верный документ модель может писать
поверх него что угодно.

Корпус здесь намеренно маленький, и абсолютные числа на нём мало что значат
— смысл имеет сравнение конфигураций между собой на одном датасете.
